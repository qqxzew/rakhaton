# Data Model: PACS Comparator Check

## Boundaries and persistence

- **Clinical facts and derived clinical/workflow records** are read and written as HL7 FHIR R4 through the `FhirStore` interface. `LocalBundleStore` reads patient bundles from `data/raw/fhir/` and writes generated resources under `data/fhir_out/`; `IrisFhirStore` uses the configured IRIS FHIR endpoint.
- **Application-only state** (MDT schedule, registered cases, UI/readiness snapshots, request transition log and demo clock) is kept in SQLite through SQLAlchemy. It must not become a competing source of clinical facts.
- **Untrusted or sensitive runtime content** (full report text, dataset-derived values, model cache, labels, outbox and generated voice files) remains under git-ignored `data/`.
- Patient links use the dataset pseudonymous identifier, never a name or date of birth. Fictional display names are presentation-only.

## Entities

| Entity | Fields and validation | Relationships / persistence |
|---|---|---|
| **Patient** | `id` (dataset pseudonym; required), fictional `display_name`, optional sex/age band, diagnosis codes. Do not use display name for matching. | One patient has many `Study`, source documents, `PriorReference`, `PlannedExam`, and `Case` records. Read from FHIR `Patient` and `Condition`; presentation name is generated by the app. |
| **SourceDocument** | `id`, `patient_id`, kind, authored/issued date, full text, source resource type/id. Full text never enters tracked files or info-level logs. | A FHIR `DiagnosticReport` or `DocumentReference`; a source for zero or more extracted facts. |
| **Study** | `id`/accession, `patient_id`, date, modality, normalized regions, site text, source (`internal`, `referenced`, `received`), PACS flag (`yes`, `no`, `unknown`), report id. | Internal and received studies map to FHIR `ImagingStudy`; dataset accessions remain unique within patient. References can point to a matching internal study. |
| **PriorReference** | `id`, patient/report ids, modality, region set, date as written and normalized with precision, optional site text, exact `quote`, confidence in `[0,1]`, date-valid flag, matched study id. A quote must be an exact substring (whitespace normalization may be used only for validation). | Extracted from a `DiagnosticReport`; written as FHIR `Observation` with category `imaging-reference`, plus `Provenance` referencing the source and extraction agent/model. |
| **PlannedExam** | `id`, patient id, modality, region set, absolute date or relative interval resolved against source date, target site, source document id, exact quote, confidence; coordinator may correct the fields. | One active exam can be linked to a `Case`. Persist as FHIR `ServiceRequest` and `Provenance`. |
| **Meeting** | `id`, date/time, label, eligible diagnosis-group ids, `accepts_registrations`. Eligibility comes only from configuration. | Has many `Case` records. Schedule is generated/configured app state, not inferred by AI. |
| **Case** | `id`, patient and meeting ids, optional planned-exam id, reference date, per-patient date offset, check status (`pending`, `running`, `done`, `failed`), readiness (`not_ready`, `attention`, `ready`) and reason, timestamps. Unique `(patient_id, meeting_id)`. Pipeline dates remain in the patient's shifted frame; only UI dates are offset. | Belongs to one Patient and one Meeting; has many `RequiredItem` records. Rechecking is idempotent for computed items and preserves request history. |
| **RequiredItem** | `id`, case id, one or more rule ids/reasons, modality, regions, target date/window, matched study or reference id, availability (`available`, `not_in_pacs`, `unknown`, `not_found`), holding site, evidence quote/source/confidence, waiver flag and reason, optional request id. Deduplicate a study required by multiple rules while retaining every reason. | A not-ready item maps to a FHIR `Task` with patient focus/owner and due date. Its source evidence remains linked through referenced resources/`Provenance`. |
| **Provider** | `id`, canonical name, aliases, fake email/phone, working hours, language, preferred channel and exchange route. Demo contacts must be non-routable/fake. | App configuration used to resolve a likely holding site; never claim it is a live facility integration. |
| **Request** | request id, required-item/provider ids, state, approval actor/time, attempts, next-action time, outgoing/incoming `Communication` references. Approval metadata is mandatory before sending. | State changes append immutable `RequestEvent` entries and a FHIR `AuditEvent`; request workflow is mirrored to FHIR `Task` and communications to FHIR `Communication`. |
| **RequestEvent** | request id, from/to state, timestamp, actor (`system`, `coordinator`, `provider-sim`), note and optional evidence quote. | Ordered append-only business workflow history for the Request; never replace history on a recheck. This remains the authoritative transition log; `AuditEvent` is not a substitute for it. |

## FHIR resource mapping

| Use | FHIR R4 resource | Important links/content |
|---|---|---|
| Source patient | `Patient`, `Condition` | Patient id and diagnosis codes; application matching is by the pseudonymous identifier. |
| Internal reports and notes | `DiagnosticReport`, `DocumentReference` | Source ids, dates and report/note text. |
| Internal/received study | `ImagingStudy` | Accession identifier, start date, modality, patient; dataset PACS availability extension is treated as simulated evidence. |
| Planned exam | `ServiceRequest` | Modality, body site, occurrence timing and reference to source document; include the verified quote as an extension. |
| Extracted prior reference | `Observation` (category `imaging-reference`) | Components for modality, region, date and site; `derivedFrom` points to the source report. |
| Extraction provenance | `Provenance` | Source entity, software/model agent, quote and confidence extension. |
| Required-study request/task | `Task` | `focus` points to the required study/reference; `for` to Patient; owner coordinator; due date and business status reflect the request state. |
| Outgoing request / parsed reply | `Communication` | `basedOn` Task, medium, sent/received time and minimum-data payload or reply evidence. |
| Security/audit-relevant events | `AuditEvent` | Who/what/when for applicable approvals, outgoing requests and specified patient-view events. Treat it as a FHIR security/audit record, distinct from the complete business `RequestEvent` history. Confirm create support through endpoint metadata. |

The R4 JSON resources must validate against the selected server's configured FHIR R4 version and supported interactions. At IRIS startup, inspect `GET [base]/metadata`; test transaction/reference behavior with the kit instance and avoid relying on unsupported compartment-wide search, chained search, `_include`, composite parameters, `_total`, or `:missing`. App-only `Meeting`, `Case`, UI flags, demo clock and request event presentation do not get disguised as unrelated clinical FHIR facts.

## State and readiness rules

### Case checking

`pending → running → done | failed`. A new case is immediately visible as `not_ready` / “initial check running”. A failed or unavailable record load remains `not_ready` with an explicit reason. Re-running a completed case replaces computed required items but must preserve all request/event history.

### Required item

- `available`, matching verified receipt, or an explicit waiver → non-blocking.
- `unknown`, implausible date, low-confidence evidence, conflict, or a time-gap warning → attention; do not automatically create an external request from an invalid/low-confidence reference.
- `not_in_pacs` or `not_found` without verified receipt/waiver → missing.

### Request

Normal progression: `DETECTED → DRAFTED → APPROVED → SENT → ACKNOWLEDGED → RECEIVED → VERIFIED → CLOSED`.

Side outcomes: `REJECTED`, `NEEDS_INFO`, `WRONG_RECIPIENT`, `CANCELLED`, `REMINDER_SENT`, `VOICE_ESCALATED`, `HUMAN_ESCALATED`. Every transition is appended with timestamp and actor. Only a recorded approval can cause `APPROVED` and subsequent send. A received study resolves the item only after modality/date-window/region verification; a waived item remains waived even if a later simulated receipt arrives.

### Aggregate readiness

- Case: `not_ready` while checking/records unavailable or any required item is missing; `attention` for any uncertainty, pending approval, conflict, or no prior studies; otherwise `ready`.
- Meeting: most severe state of its cases; an empty meeting is `attention` with reason “no patients”.
- Day/dashboard: most severe contained meeting/case state, with counts recalculated after every case/request/waiver/verification change.

## Invariants

1. Every AI-derived clinical fact has a source resource id, exact source quote, and confidence; invalid quotes cannot be displayed as verified evidence.
2. Dates remain in patient-relative dataset time for matching; a consistent case offset is presentation-only and visibly labeled.
3. Every simulated value is marked in persisted data and the UI and is obtained through a replaceable adapter.
4. Outbound message payloads contain only the allowed request metadata and are not delivered before a durable approval event.
5. Readiness is derived from the required items and their verified/waived states, not from an LLM response.
6. Diagnosis-to-meeting eligibility is configuration-based. No name-based patient matching, diagnosis/therapy suggestions, or real clinical actions are allowed.
